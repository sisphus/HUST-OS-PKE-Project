## 1. 面试版项目介绍

### 1.1 30 秒中文版本

我在一个基于 Spike 的 RISC-V PKE 教学操作系统上，逐步实现了从 trap、系统调用、虚拟内存、进程调度到简化文件系统的多个内核机制。具体包括：补齐用户态 `ecall` 的系统调用分发和返回值路径，处理 M-mode 非法指令和定时器中断，实现用户页表地址转换、按页内存分配和栈缺页处理，完成 `fork`、`yield`、时间片轮转、`wait`、信号量和写时复制，最后在 VFS/RFS 上实现文件创建、目录读取和硬链接。

项目中比较有代表性的工作有两类：第一类是区分 per-hart 状态和全局共享资源，第二类是判断一个 trap 应该继续、重试还是终止。例如系统调用要跳过 `ecall`，页错误要保持原 PC 重试，非法地址则必须终止。我还修复了当前工具链生成的 ELF 装载段超过一页导致的加载器兼容性问题。

### 1.2 30 秒英文版本

I implemented and verified a sequence of kernel mechanisms in a RISC-V PKE proxy kernel running on Spike. The work covered trap handling, system calls, virtual memory, process creation and scheduling, synchronization, copy-on-write, and a layered file system.

I completed the user `ecall` path, M-mode illegal-instruction and timer handling, page-table translation, page allocation and page faults, `fork`, cooperative and preemptive scheduling, `wait`, semaphores, copy-on-write, and RFS file, directory, and hard-link operations.

The main engineering lessons were separating per-hart state from shared state, preserving the correct trap context, and deciding whether a fault should be retried or should terminate the process. I also extended the ELF loader to handle multi-page load segments generated by the current toolchain.

### 1.3 3 分钟展开顺序

面试官继续追问时，按以下顺序讲最清楚：

1. 运行模型：Spike 启动 M-mode，部分 trap 被委托给 S-mode，用户程序运行在 U-mode；
2. trap 主线：系统调用、定时器和页错误分别进入不同处理分支；
3. 内存：Sv39 页表把用户虚拟地址转换为物理地址，缺页时按当前进程建立映射；
4. 进程：`fork` 复制上下文，代码可以共享，数据需要隔离，COW 把复制推迟到写入；
5. 调度和同步：READY 队列、`yield`、时间片、阻塞队列、信号量和多 hart 资源保护；
6. 文件系统：VFS 提供抽象，RFS 维护 inode、目录项和数据块，硬链接只增加名字和链接数；
7. 局限性：这是教学内核，页表回收、用户指针校验、事务性更新和通用多核调度仍可加强。

## 2. 总体架构

### 2.1 特权级分工

~~~text
                     Spike 模拟硬件
       CLINT timer / HTIF / DRAM / device tree
                         │
                         ▼
┌────────────────────────────────────────────────────────┐
│ M-mode：machine startup                                 │
│  - 读取 hartid 和 DTB                                   │
│  - 初始化 machine stack、trap vector、timer             │
│  - 设置 medeleg/mideleg，把部分 trap 委托给 S-mode       │
└────────────────────────────────────────────────────────┘
                         │ mret
                         ▼
┌────────────────────────────────────────────────────────┐
│ S-mode：PKE kernel                                      │
│  - 进程、调度、系统调用、页表、物理页和 VFS              │
│  - 保存用户 trapframe，处理 syscall/page fault/interrupt │
└────────────────────────────────────────────────────────┘
                         │ sret
                         ▼
┌────────────────────────────────────────────────────────┐
│ U-mode：user application                                │
│  - 普通计算、访问用户地址                               │
│  - 通过 ecall 请求内核服务                              │
└────────────────────────────────────────────────────────┘
~~~

核心边界：

- M-mode 处理没有委托给 S-mode 的机器级事件，例如非法特权指令和机器定时器中断；
- S-mode 处理被委托的用户系统调用、用户页错误和 S-mode 软件中断；
- U-mode 不能直接访问特权 CSR、内核页表或文件系统设备。

### 2.2 四条关键路径

系统调用：

~~~text
user library
  → a0-a7 准备系统调用号和参数
  → ecall
  → S-mode trap vector
  → current->trapframe
  → handle_syscall()
  → do_syscall()
  → tf->regs.a0 保存返回值
  → epc += 4
  → sret 回到用户态
~~~

用户页错误：

~~~text
U-mode 访问未映射页面
  → hardware 写入 scause/stval/sepc
  → S-mode trap
  → 根据地址范围判断合法性
  → alloc_page + user_vm_map
  → 保持 sepc 不变
  → 返回后重试原指令
~~~

定时器和抢占：

~~~text
CLINT mtime >= mtimecmp
  → M-mode MTIP
  → 安排下一次 mtimecmp
  → 设置 SIP_SSIP
  → S-mode SSIP
  → tick++，清除 SIP_SSIP
  → 时间片耗尽时把 current 放回 READY 队列
  → schedule()
~~~

文件操作：

~~~text
user open/read/write/link/unlink
  → user library
  → syscall
  → kernel/proc_file.c
  → kernel/vfs.c
  → vinode->i_ops
  → RFS 或 hostfs
  → inode / directory entry / data block
~~~

## 3. 核心数据结构和寄存器

### 3.1 Trap 相关 CSR

| CSR | 所属场景 | 作用 |
| --- | --- | --- |
| `mtvec` | M-mode | M-mode trap 入口 |
| `stvec` | S-mode | S-mode trap 入口 |
| `mepc` | M-mode | M-mode trap 发生时的 PC |
| `sepc` | S-mode | S-mode trap 发生时的 PC |
| `mcause` | M-mode | M-mode 异常或中断原因 |
| `scause` | S-mode | S-mode 异常或中断原因 |
| `mtval` | M-mode | M-mode fault 附加地址/信息 |
| `stval` | S-mode | S-mode fault 附加地址/信息 |
| `mscratch` | M-mode | trap 入口临时保存区/中断帧指针 |
| `sscratch` | S-mode | 用户 trapframe 指针 |
| `medeleg` | M-mode | 哪些异常委托给 S-mode |
| `mideleg` | M-mode | 哪些中断委托给 S-mode |
| `sip` | S-mode | S-mode pending interrupt 状态 |
| `sie` | S-mode | S-mode interrupt enable |
| `mtime` | CLINT | 当前机器计数器 |
| `mtimecmp` | CLINT | 当前 hart 下一次定时器触发点 |

最容易混淆的是：

- `mepc` 和 `sepc`：取决于当前 trap handler 运行在哪个特权级；
- `mcause` 和 `scause`：同样取决于当前 trap 级别，不能因为异常来自用户态就随便读取其中一个。

### 3.2 `trapframe`

用户程序进入 S-mode trap 时，汇编入口把用户寄存器保存到当前进程的 trapframe：

~~~text
current->trapframe->regs.a0-a7  系统调用号和参数
current->trapframe->regs.sp     用户态栈指针
current->trapframe->regs.s0     用户态 frame pointer
current->trapframe->regs.tp     用户态保留的 hart 身份
current->trapframe->epc         用户态应该恢复的 PC
kernel_sp                       进入内核后使用的栈
kernel_satp                     内核页表
kernel_trap                     S-mode trap handler 地址
~~~

进入内核后，当前 C 函数的 `sp` 已经是内核栈。因此调试用户程序时不能直接沿当前 `sp` 回溯，必须使用 `current->trapframe->regs.sp` 和 `current->trapframe->regs.s0`。

### 3.3 `process`

`process` 保存一个用户进程的运行上下文和资源：

~~~text
pagetable       用户页表根地址
trapframe       用户寄存器保存区
kstack          用户进程进入内核时使用的内核栈
mapped_info     代码、数据、堆、栈等区域元数据
user_heap       简化堆的虚拟地址游标和释放页列表
pid/status      进程身份和 READY/RUNNING/BLOCKED/ZOMBIE 状态
parent          父进程
queue_next      就绪队列或同步等待队列链接
tick_count      当前时间片已经消耗的 tick
pfiles          该进程的文件描述符表
~~~

### 3.4 页表和 PTE

PKE 使用 Sv39，虚拟地址被划分为三级页表索引和 12 位页内偏移：

~~~text
VA = VPN[2] | VPN[1] | VPN[0] | page offset
                 9 bits each       12 bits
~~~

叶子 PTE 包含物理页号、有效位和权限位。 `page_walk()` 返回叶子 PTE 的地址；`PTE2PA(*pte)` 才能取出物理页起始地址，最后还要加页内偏移。

### 3.5 VFS/RFS 对象

~~~text
super_block
  └── s_root: 根目录 dentry

dentry
  ├── name
  ├── parent
  └── dentry_inode

vinode
  ├── inum
  ├── size/type/nlinks/blocks
  ├── addrs[]
  ├── sb
  └── i_ops

file
  ├── f_dentry
  ├── offset
  ├── readable/writable
  └── status
~~~

其中：

- `dentry` 表示路径中的一个名字；
- `vinode` 表示文件对象和 inode 内容；
- `file` 表示一次打开实例，拥有独立的文件偏移；
- `i_ops` 决定实际由 RFS 还是 hostfs 执行底层操作。

## 4. Lab1：从 trap 到多核启动

### 4.1 Lab1.1：系统调用路径

目标是打通 `printu()` 和 `exit()` 的最小用户态系统调用链：

~~~text
user/app_helloworld.c
  → printu()
  → user/user_lib.c: do_user_call()
  → a0 = syscall number, a1... = arguments
  → ecall
  → kernel/strap_vector.S 保存所有用户寄存器
  → current->trapframe
  → kernel/strap.c: handle_syscall()
  → kernel/syscall.c: do_syscall()
  → sys_user_print()
~~~

`handle_syscall()` 的关键实现：

~~~c
tf->epc += 4;
tf->regs.a0 = do_syscall(tf->regs.a0, tf->regs.a1, tf->regs.a2,
                         tf->regs.a3, tf->regs.a4, tf->regs.a5,
                         tf->regs.a6, tf->regs.a7);
~~~

#### 为什么 `epc += 4`

`sepc` 指向触发 trap 的 `ecall` 本身。 `ecall` 已经被内核处理过，返回用户态时必须跳到下一条指令。当前 `rv64imafd` 构建中普通指令是 4 字节，因此加 4。

如果不加 4：

~~~text
sret 回到原 ecall
  → 再次进入内核
  → 再次处理同一个系统调用
  → 系统调用循环
~~~

#### 为什么要把返回值写回 `a0`

RISC-V ABI 使用 `a0` 保存返回值。用户态 `do_user_call()` 从恢复后的 `a0` 取得系统调用结果。如果不写回，`a0` 可能仍然是旧的系统调用号，例如 `printu()` 可能得到 64。当前 Hello World 没有使用这个返回值，所以表面上仍可能打印成功，但实现是不完整的。

#### 重要边界

Lab1 使用 Bare mode，用户地址和物理地址暂时相同，所以内核可以直接使用用户传入的 `buf`。Lab2 开启分页后，用户指针必须通过当前进程的页表转换。

源码：[kernel/strap.c](/Users/weileipeng/Desktop/gradCourses/MIT6.1810-OS/PKE/riscv-pke/kernel/strap.c)。

### 4.2 Lab1.2：U-mode 非法特权指令

用户程序执行：

~~~c
asm volatile("csrw sscratch, 0");
~~~

这条指令的编码本身合法，但 `sscratch` 是特权 CSR，U-mode 没有权限写它，因此硬件报告：

~~~text
CAUSE_ILLEGAL_INSTRUCTION = 2
~~~

普通的 `addi a0, a0, 1` 不访问特权 CSR，所以 U-mode 可以正常执行。

#### 为什么进入 M-mode

`delegate_traps()` 只把部分异常委托给 S-mode，例如用户 `ecall`、页错误和断点。非法指令没有放进 `medeleg`，所以路径是：

~~~text
U-mode
  → M-mode mtrapvec
  → 保存 g_itrframe
  → handle_mtrap()
  → CAUSE_ILLEGAL_INSTRUCTION
  → handle_illegal_instruction()
  → panic()
~~~

不能调用 `do_syscall()`，因为这里没有发生 `ecall`，也没有系统调用号；这是一个 M-mode 异常分发问题。

#### `mscratch` 交换

M-mode trap 入口先执行类似：

~~~asm
csrrw a0, mscratch, a0
~~~

假设进入 trap 前：

~~~text
a0       = 用户原始 a0
mscratch = &g_itrframe
~~~

交换后：

~~~text
a0       = &g_itrframe
mscratch = 用户原始 a0
~~~

这样汇编入口可以用 `a0` 作为寄存器保存区基址，随后再把原来的用户 `a0` 写回 trapframe。否则恢复后用户 `a0` 会错误地变成中断帧地址。

#### 为什么不推进 `mepc`

这里的处理函数最终 `panic` 并关机，不会正常返回用户态。如果只是打印错误后返回而不修改 `mepc`，CPU 会再次执行同一条非法指令，形成异常循环。

源码：[kernel/machine/mtrap.c](/Users/weileipeng/Desktop/gradCourses/MIT6.1810-OS/PKE/riscv-pke/kernel/machine/mtrap.c)。

### 4.3 Lab1.3：定时器中断

CLINT 提供：

~~~text
mtime     当前计数器，持续增长
mtimecmp  下一次触发时间点
~~~

当 `mtime >= mtimecmp` 时，硬件产生机器定时器中断 `MTIP`。

M-mode 的 `handle_timer()` 做硬件相关的两件事：

1. 把当前 hart 的 `mtimecmp` 向后推进一个 `TIMER_INTERVAL`，安排下一次中断；
2. 设置 `sip.SIP_SSIP`，制造一个已委托给 S-mode 的软件中断。

随后 S-mode 收到 `SSIP`，进入 `handle_mtimer_trap()`：

~~~c
sprint("Ticks %d\n", g_ticks);
g_ticks++;
write_csr(sip, read_csr(sip) & ~SIP_SSIP);
~~~

只清除 `SIP_SSIP`，而不是把整个 `sip` 写成 0，是为了保留其他可能的 pending 位。定时器是异步事件，不对应某条已处理完的用户指令，所以不修改 `sepc`。

源码：[kernel/strap.c](/Users/weileipeng/Desktop/gradCourses/MIT6.1810-OS/PKE/riscv-pke/kernel/strap.c)。

### 4.4 Lab1 Challenge 1：用户调用栈回溯

目标是用户调用 `print_backtrace(7)` 时输出 `f8` 到 `f2`。

#### 系统调用层

新增：

~~~c
#define SYS_user_print_backtrace (SYS_user_base + 2)
~~~

用户库把深度放入 `a1`，系统调用号放入 `a0`。已有 `handle_syscall()` 继续负责 `epc += 4` 和返回值。

#### 沿用户 frame pointer 回溯

内核处理函数的当前 `sp` 是内核栈，不能拿它当用户栈。正确起点是：

~~~text
fp = current->trapframe->regs.s0
~~~

构建时使用 `-fno-omit-frame-pointer` 保留 frame pointer。本次构建中普通函数序言大致是：

~~~asm
addi sp, sp, -16
sd   ra, 8(sp)
sd   s0, 0(sp)
addi s0, sp, 16
~~~

所以：

~~~text
保存的 ra   = *(fp - 8)
保存的旧 fp = *(fp - 16)
~~~

发生 `ecall` 时最顶层 frame 属于 `do_user_call()`，它的栈帧布局不同。实现先跳过这一层，再开始输出用户函数。

#### ELF 地址到函数名

返回地址需要查询 ELF：

| ELF section | 用途 |
| --- | --- |
| `.shstrtab` | section 名称，例如 `.symtab`、`.strtab` |
| `.symtab` | 符号记录，包括函数起始地址、大小和名字偏移 |
| `.strtab` | 保存真正的符号名字符串，例如 `f8`、`main` |

若：

~~~text
st_value <= ra < st_value + st_size
~~~

则返回地址属于该函数，再通过 `st_name` 从 `.strtab` 取得名称。程序加载完成后保留 host ELF 文件句柄，回溯时用 `spike_file_pread()` 读取符号表。

### 4.5 Lab1 Challenge 2：运行时错误定位到源码行

目标是把：

~~~text
Illegal instruction
~~~

提升为：

~~~text
Runtime error at user/app_errorline.c:13
  asm volatile("csrw sscratch, 0");
~~~

编译器通过 `-gdwarf-3` 生成 `.debug_line`，其中保存：

~~~text
机器地址 → 文件索引、行号
文件索引 → 目录索引、文件名
目录索引 → 目录字符串
~~~

实现扫描 ELF section header，通过 `.shstrtab` 找到 `.debug_line`，读取并解析 line program。异常地址通常落在一段机器指令的中间，不一定和表中的地址完全相等，因此选择 `addr <= fault_pc` 的最后一条映射。

非法特权指令在 M-mode 处理，所以使用 `mepc`；S-mode fallback 才使用 `sepc`。解析出路径和行号后，还要用 host 文件接口打开源文件，逐行读取出错行。最后仍然 `panic`，因为这个异常不可恢复。

这条链路是：

~~~text
mepc
  → .debug_line
  → 文件路径和行号
  → host 文件接口
  → 源代码文本
  → panic
~~~

### 4.6 Lab1 Challenge 3：多 hart 启动和退出同步

使用两个 hart：

~~~bash
spike --isa=rv64imafd -p2 obj/riscv-pke obj/app0 obj/app1
~~~

进入 `_mentry` 时 Spike 通过 `a0` 传入 hart 编号，通过 `a1` 传入 DTB 地址。M-mode 将 hart 编号写入 `tp`，后续 S-mode 通过 `read_tp()` 取得当前 hart。创建用户 trapframe 时也要写入 `regs.tp`，否则 `return_to_user()` 恢复后用户态身份会错误。

per-hart 资源和共享资源要分别处理：

| 资源 | 处理方式 | 原因 |
| --- | --- | --- |
| M/S-mode CSR | 每 hart 独立 | 每个 hart 有独立执行上下文 |
| machine stack | 每 hart 独立 | M-mode C 调用栈不能重叠 |
| `g_itrframe` | 每 hart 独立 | trap 不能覆盖彼此的寄存器保存区 |
| `current` | 每 hart 独立 | 不能让 hart1 覆盖 hart0 的进程指针 |
| 用户 stack/kstack/trapframe | 每 hart 独立 | 运行时内存不能互相覆盖 |
| `g_ticks` | 每 hart 独立 | timer 事件独立 |
| HTIF、DTB | 共享且一次初始化 | 描述同一个模拟器环境 |
| 物理页空闲链表 | 共享且加锁 | 物理内存池由所有 hart 使用 |
| 启动/退出计数器 | 共享且原子更新 | 用于阶段同步 |

锁保护短临界区，例如空闲页链表的 head；barrier 保证所有 hart 完成一个阶段后再继续，例如 hart0 完成 HTIF/DTB 初始化后，所有 hart 才进入 S-mode。

跳过内核参数后：

~~~text
hart0 → argv[0] → app0
hart1 → argv[1] → app1
~~~

两个进程可以都使用 `0x400000` 作为堆起始虚拟地址，因为它们的页表不同：

~~~text
process0 page table: 0x400000 → P0
process1 page table: 0x400000 → P1
~~~

退出时不能由第一个 hart 直接 shutdown。两个 hart 先原子递增独立的 `exit_count`，都到达 barrier 后只让 hart0 执行全局关机。

## 5. Lab2：分页、分配和缺页

### 5.1 Lab2.1：用户虚拟地址到物理地址

`user_va_to_pa(page_dir, va)` 只负责查询已有映射，不负责创建映射：

~~~c
pte_t *pte = page_walk(page_dir, (uint64)va, 0);
if (pte == 0 || (*pte & PTE_V) == 0)
  return NULL;

return (void *)(PTE2PA(*pte) + ((uint64)va & (PGSIZE - 1)));
~~~

`alloc == 0` 表示遍历失败时不创建中间页表；地址转换函数不应该因为用户传入非法地址而修改页表。必须使用指定的 `page_dir`，通常是 `current->pagetable`，因为相同虚拟地址在不同进程中可能指向不同物理页。

PTE 保存的是物理页起始地址，低 12 位页内偏移必须补回：

~~~text
VA                 = 0x12345
页内偏移            = 0x345
物理页起始地址       = 0x80012000
最终物理地址         = 0x80012345
~~~

源码：[kernel/vmm.c](/Users/weileipeng/Desktop/gradCourses/MIT6.1810-OS/PKE/riscv-pke/kernel/vmm.c)。

### 5.2 Lab2.2：按页分配和回收

这是教学用的单页分配器：

~~~text
一次 naive_malloc → 一个物理页 + 一个用户虚拟页
一次 naive_free   → 解除一个 PTE + 可选回收一个物理页
~~~

分配路径：

~~~text
alloc_page()
  → 取得物理页 pa
  → 从 g_ufree_page 取得用户虚拟地址 va
  → g_ufree_page += PGSIZE
  → user_vm_map(current->pagetable, va, PGSIZE, pa, permissions)
  → 返回 va
~~~

释放路径：

~~~text
page_walk(current->pagetable, va, 0)
  → 检查 PTE_V
  → 先读取 PTE2PA(*pte)
  → free_page(pa)
  → *pte = 0
~~~

必须先保存物理地址，因为清除 PTE 后就失去了原物理页号。释放用户虚拟地址时，也必须查当前进程页表，不能把 `va` 直接传给 `free_page()`。

`g_ufree_page` 只递增、不回退，因此可以释放物理资源，但不会复用历史虚拟地址。这是课程范围内的简化，不是通用堆分配器。

### 5.3 Lab2.3：用户栈缺页

初始只映射一个用户栈页，用户栈从 `USER_STACK_TOP` 向低地址增长。递归调用增加栈帧后，合法存储指令可能访问未映射的下一页，触发 `CAUSE_STORE_PAGE_FAULT`。

处理流程：

1. 从 `stval` 读取 fault 字节地址；
2. 使用 `ROUNDDOWN(stval, PGSIZE)` 得到页首；
3. `alloc_page()` 分配物理页；
4. 使用 `current->pagetable` 建立用户读写映射；
5. 保持 `sepc` 不变，返回后重试原存储指令。

例如：

~~~text
stval             = 0x7fffdff8
缺页虚拟页起始地址 = 0x7fffd000
~~~

页错误时原存储指令还没有完成，因此不能把 `sepc` 加 4。

### 5.4 Lab2 Challenge 1：合法和非法缺页

仅凭 `scause == CAUSE_STORE_PAGE_FAULT` 不能决定是否分配页面，因为合法栈增长和非法堆越界可能拥有同一个原因码。

当前挑战把地址分为：

~~~text
stval 在 [USER_STACK_TOP - USER_STACK_MAX_PAGES * PGSIZE,
          USER_STACK_TOP) 内 → 合法栈缺页
否则 → 非法地址
~~~

合法栈缺页分配并映射页面；非法地址打印错误并 `shutdown(-1)`。不能让非法 fault 原样返回，否则 CPU 会重复执行同一条非法存储指令，形成无限 fault 循环。

这是“硬件原因码 + 进程地址空间策略”的组合：硬件只告诉内核发生了 store page fault，内核还要用 `stval` 和区域边界判断是否可恢复。

### 5.5 Lab2 Challenge 3：多核内存管理

如果物理页空闲链表没有锁：

~~~text
hart0 读到 head = P
hart1 也读到 head = P
hart0 返回 P
hart1 也返回 P
~~~

两个进程会同时使用同一个物理页。实现使用 RISC-V 原子指令实现自旋锁，保护空闲链表取出和插入。锁只覆盖短临界区，不能覆盖整个页表映射过程，因为映射过程可能再次分配页表页。

`g_ufree_page` 不能作为所有进程共享的全局游标。每个 `process` 保存自己的堆游标，所以不同进程都可以从 `USER_FREE_ADDRESS_START` 开始：

~~~text
process0: 0x400000 → P0
process1: 0x400000 → P1
~~~

Lab1 Challenge 3 主要解决 per-hart 的启动、trapframe、current、用户地址和退出同步；本挑战进一步解决共享物理页分配器的并发安全。

## 6. Lab3：进程、调度和同步

### 6.1 Lab3.1：`fork()`

调用链：

~~~text
user fork()
  → ecall
  → handle_syscall()
  → sys_user_fork()
  → do_fork(parent)
~~~

`do_fork()` 创建子进程、准备自己的页表和 trapframe，然后复制父进程上下文。父进程的系统调用返回值是子 PID；子进程的 trapframe 强制设置：

~~~c
child->trapframe->regs.a0 = 0;
~~~

所以同一条 `fork()` 返回点有不同结果：

~~~text
父进程 → child_pid
子进程 → 0
~~~

#### 代码共享、数据复制

代码段是只读可执行的，父子页表可以映射同一个物理代码页：

~~~text
parent page table: VA → code PA
child  page table: VA → code PA
~~~

数据段包含全局变量和可修改状态，必须分配新物理页并复制：

~~~text
parent data VA → parent data PA
child  data VA → child data PA
~~~

代码映射完成后还要登记到子进程的 `mapped_info`。页表解决“能否访问”，`mapped_info` 解决“进程后续遍历时是否知道这块区域存在”。

源码：[kernel/process.c](/Users/weileipeng/Desktop/gradCourses/MIT6.1810-OS/PKE/riscv-pke/kernel/process.c)。

### 6.2 Lab3.2：协作式 `yield()`

`yield()` 让当前进程主动放弃 CPU，但进程仍然可运行：

~~~c
current->status = READY;
insert_to_ready_queue(current);
schedule();
~~~

必须重新入队，否则当前进程会从调度器候选集合中消失；必须放到队尾，否则调度器可能立即再次选择它。这里的 ready queue 是 FIFO：

~~~text
当前进程出队运行
  → yield
  → 当前进程入队尾
  → 队首的另一个 READY 进程运行
~~~

### 6.3 Lab3.3：时间片轮转

Lab3.2 需要应用显式调用 `yield()`。Lab3.3 的长循环不主动让出 CPU，所以由定时器累计 tick，达到时间片后调用 `rrsched()`：

~~~c
if (++current->tick_count >= TIME_SLICE_LEN) {
  current->tick_count = 0;
  current->status = READY;
  insert_to_ready_queue(current);
  schedule();
}
~~~

当前 `TIME_SLICE_LEN` 为 2：

~~~text
第 1 个 tick：0 → 1，继续当前进程
第 2 个 tick：1 → 2，清零并切换
~~~

每次 tick 都切换会使时间片过短；达到阈值后不清零会使进程重新运行后立即被切走。

### 6.4 Lab3 Challenge 1：数据段隔离和 `wait()`

#### 数据段隔离

`fork()` 的代码可以共享，数据段必须复制。这样父、子、孙进程拥有相同的虚拟地址，但不同的物理数据页。例如：

~~~text
parent flag = 0
child  flag = 1
grandchild flag = 2
~~~

#### `wait(pid)` 规则

父进程先检查 `child->parent == current`，只考虑自己的子进程：

~~~text
pid == -1 → 等待任意子进程
pid > 0   → 等待指定 PID
其他值    → 返回 -1
~~~

没有匹配子进程返回 `-1`；匹配子进程已经是 `ZOMBIE` 时返回子 PID；匹配子进程仍在运行时，父进程变为 `BLOCKED` 并让出 CPU。

子进程退出时：

~~~text
子进程 RUNNING → ZOMBIE
父进程 trapframe->regs.a0 = child_pid
父进程 BLOCKED → READY
父进程重新运行后从 wait() 得到 child_pid
~~~

当前框架的 `free_process()` 不能总是立即安全地拆除正在使用的完整地址空间。因此进程槽位可以标记为 `FREE`，但页表和物理页的完整回收仍是已知限制。

### 6.5 Lab3 Challenge 2：信号量

内核固定维护信号量数组，每个槽位包含：

~~~c
typedef struct semaphore_t {
  int used;
  int count;
  process *wait_queue_head;
  process *wait_queue_tail;
} semaphore;
~~~

P 操作：

~~~text
count > 0 → count--，当前进程继续
count == 0 → 进入该信号量等待队列，状态 BLOCKED，schedule()
~~~

阻塞进程不能留在普通 READY 队列，否则调度器会错误运行它。等待队列复用 `process.queue_next`，因为进程此时不在 ready queue 中。

V 操作：

~~~text
没有等待者 → count++
有等待者   → 取队首一个进程，改为 READY，放回 ready queue
~~~

有等待者时不递增 `count`，因为释放的资源直接交给被唤醒的进程；一次 V 只唤醒一个进程。

### 6.6 Lab3 Challenge 3：写时复制 COW

普通 `fork()` 在创建子进程时立即复制 heap 页面。COW 把复制推迟到真正写入：

~~~text
fork 后：父子共享同一个物理页，只读
某一方写入：触发 store page fault
缺页处理：分配新页、复制旧内容、恢复写权限
之后：写入方使用新页，另一方继续使用旧页
~~~

使用 PTE 的 RSW 软件保留位：

~~~c
#define PTE_COW (1L << 8)
~~~

COW 页满足：

~~~text
PTE_V = 1
PTE_R = 1
PTE_W = 0
PTE_COW = 1
~~~

父子双方都必须去掉 `PTE_W`。只修改子进程会让父进程继续直接写共享页，绕过 COW。

fork 阶段：

~~~text
读取父进程 PTE 指向的物理页 P
父 PTE：清除 W，设置 COW
子 PTE：映射相同 P，清除 W，设置 COW
P 的物理引用计数 +1
~~~

写 fault 阶段：

~~~text
PTE 无效             → 普通栈缺页路径
PTE 有效且 PTE_COW   → 读取旧页 P
                       分配新页 Q
                       memcpy(Q, P, PGSIZE)
                       当前 PTE 指向 Q
                       设置 W，清除 COW
                       刷新 TLB
                       保持 sepc，重试原写指令
~~~

物理页引用计数避免共享页被第一个解除映射的进程错误释放：

~~~text
fork 后               P.ref = 2
子进程 COW 复制后      P.ref = 1
最后一个持有者释放后  P.ref = 0，才回到空闲页链表
~~~

## 7. Lab4：VFS、RFS 和硬链接

### 7.1 分层结构

~~~text
user API
  → syscall wrapper
  → kernel syscall handler
  → process file table
  → VFS abstraction
  → vinode i_ops
  → RFS 或 hostfs
~~~

`i_ops` 是底层实现选择点。VFS 的上层流程不需要了解 RFS 的 inode 块布局，也能支持 hostfs 等不同后端。

### 7.2 RFS 磁盘布局

RFS 使用 RAM disk，关键块编号：

| 区域 | 块 |
| --- | --- |
| super block | 0 |
| inode 区 | 从 1 开始 |
| bitmap | 11 |
| data block free area | 12 开始 |

磁盘 inode：

~~~c
struct rfs_dinode {
  int size;
  int type;
  int nlinks;
  int blocks;
  int addrs[RFS_DIRECT_BLKNUM];
};
~~~

目录数据块保存连续目录项：

~~~c
struct rfs_direntry {
  int inum;
  char name[RFS_MAX_FILE_NAME_LEN];
};
~~~

目录的本质是：

~~~text
name → inode number
~~~

### 7.3 Lab4.1：创建文件和初始化 inode

`rfs_create()` 找到 `R_FREE` 的磁盘 inode 后初始化：

~~~c
free_dinode->size = 0;
free_dinode->type = R_FILE;
free_dinode->nlinks = 1;
free_dinode->blocks = 1;
~~~

然后分配第一个数据块，把 inode 写回 RAM disk，构造运行时 `vinode`，最后向父目录追加目录项。

`size`、`type`、`nlinks`、`blocks` 是持久化状态。只修改内存中的 `vinode` 不够，必须调用 `rfs_write_dinode()` 或 `rfs_write_back_vinode()` 写回磁盘 inode。

### 7.4 Lab4.2：读取目录项

打开目录时，`rfs_hook_opendir()` 把目录数据块读入缓存：

~~~text
dir_vinode->i_fs_info → rfs_dir_cache
~~~

`rfs_readdir()` 中的 `offset` 表示第几个目录项，而不是字节偏移：

~~~text
offset = 0 → 第一个目录项
offset = 1 → 第二个目录项
~~~

读到一个目录项后：

~~~c
strcpy(dir->name, p_direntry->name);
dir->inum = p_direntry->inum;
~~~

成功返回 0 并递增 offset；没有更多目录项返回 -1。

### 7.5 Lab4.3：硬链接

硬链接不复制文件内容，也不创建第二个 inode：

~~~text
ramfile  ─┐
          ├──> inode 1 ───> 同一组数据块
ramfile2 ─┘
~~~

`vfs_link()` 已经完成路径检查：原文件存在、原对象是普通文件、新路径不存在、父目录存在。RFS 的 `rfs_link(parent, sub_dentry, link_node)` 完成：

1. `link_node->nlinks++`；
2. `rfs_add_direntry(parent, sub_dentry->name, link_node->inum)`；
3. `rfs_write_back_vinode(link_node)` 把链接数写回磁盘 inode。

如果追加目录项失败，代码撤销内存中的链接数增加并返回 `-1`。

目录项保存的是名字和 inode 编号，不是文件数据。两个目录项写入相同的 `inum`，VFS 查找两个名字后就会得到同一个 `vinode` 和同一组数据块。

删除目录项时 `rfs_unlink()` 把 `nlinks` 减 1。只有 `nlinks == 0` 才释放数据块并把磁盘 inode 标记为 `R_FREE`。所以删除原路径后，剩余路径仍然可以读取文件内容。

### 7.6 ELF 多页装载的必要前置修复

在进入硬链接逻辑前，`app_hardlink` 首次运行曾经停在 ELF loader 的：

~~~c
kassert(size < PGSIZE);
~~~

原因不是硬链接，而是当前编译器生成的第一个 LOAD segment：

~~~text
FileSiz/MemSiz = 0x134c = 4940 bytes
PGSIZE          = 4096 bytes
~~~

原 loader 只分配一个物理页，并把整段内容一次性读进去，超过页边界会导致断言或越界。修复后的策略是：

~~~text
segment_start = ROUNDDOWN(vaddr, PGSIZE)
segment_end   = ROUNDUP(vaddr + memsz, PGSIZE)
npages        = (segment_end - segment_start) / PGSIZE

for every page:
    alloc_page()
    清零
    建立单页映射

按 page boundary 分段读取 filesz
memsz - filesz 区域保持为零
根据 ELF flags 设置 R/W/X 权限
~~~

这个修复体现了一个工程判断：不能只删除断言，必须同时保证物理内存足够、虚拟页映射完整、文件读取不越界，并正确处理 BSS 零填充。

## 8. 横向机制：最值得在面试中讲清楚的判断

### 8.1 什么时候 PC 加 4，什么时候不加

| 场景 | PC 处理 | 原因 |
| --- | --- | --- |
| 用户 `ecall` | `sepc += 4` | `ecall` 已由内核处理，要跳过它 |
| 合法栈 page fault | 保持 `sepc` | 原访存指令未完成，要修复映射后重试 |
| COW store fault | 保持 `sepc` | 复制并恢复写权限后重试原写指令 |
| 定时器中断 | 保持 `sepc` | 异步中断没有需要跳过的用户指令 |
| 不可恢复非法指令 | 终止，不返回 | 返回同一 `mepc` 会再次 fault |

### 8.2 什么时候用虚拟地址，什么时候用物理地址

~~~text
用户程序看到       → 虚拟地址 VA
当前进程页表保存    → VA 到 PA 的映射
PTE2PA(*pte)        → 物理页起始地址
free_page()         → PMM 管理的物理页起始地址
~~~

典型错误是用户传入 `0x400000\)，直接把它当物理页传给 `free_page()`。正确做法是先在 `current->pagetable` 中查 PTE，得到物理地址。

### 8.3 什么时候使用当前进程页表

所有“解释用户虚拟地址”的动作都需要当前进程页表：

- 用户指针转换；
- 堆和栈映射；
- 页错误的 PTE 查询；
- COW fault 的物理页定位；
- fork 时读取父进程代码或数据映射。

fork 时如果使用 `child->pagetable` 查父进程地址，或者使用全局内核页表查用户地址，都会得到错误结果。

### 8.4 lock 和 barrier 的区别

~~~text
lock：    保护一个临界区，保证同一时刻一个执行者修改共享状态
barrier： 保护阶段顺序，保证所有参与者到齐后再继续
~~~

物理页空闲链表要 lock；HTIF 一次初始化完成后所有 hart 再继续要 barrier。只用 lock 不能表达“hart1 必须等待 hart0 初始化完成”。

### 8.5 运行时引用和持久化链接数

文件系统同时有：

- VFS `vinode->ref`：内核运行时对象仍被多少 dentry/file 引用；
- inode `nlinks`：磁盘上有多少目录名指向这个 inode。

关闭文件、删除 dentry、释放 `vinode` 主要影响运行时引用；创建硬链接和 unlink 影响磁盘链接数。只有运行时引用和链接数都不再需要时，才能安全释放底层 inode 和数据块。

## 10. 高频面试问题和回答模板

### Q1：你在这个 OS 项目中具体做了什么？

我完成了从底层 trap 到文件系统的一组渐进式内核功能。早期实现了用户 `ecall` 的寄存器保存、系统调用分发、返回值和 PC 恢复，之后处理 M-mode 非法指令和定时器中断。分页阶段实现了 Sv39 用户地址转换、单页分配回收、合法栈缺页和非法地址拒绝。进程阶段实现了 `fork`、代码共享、数据复制、`yield`、时间片轮转、`wait`、信号量和 COW。最后基于 VFS/RFS 实现了文件 inode 初始化、目录读取和硬链接。我对每个阶段都用 Spike 跑了课程应用，并记录了 per-hart 状态、共享资源同步以及异常恢复点。

### Q2：为什么系统调用返回时 `sepc` 要加 4，页错误却不能加？

系统调用的 `ecall` 是一条已经被内核解释完成的指令，因此返回时必须跳过它，否则会再次进入同一个系统调用。页错误发生时，原来的 load/store 还没有完成；内核补页后要重新执行它，所以保持 `sepc` 不变。定时器是异步事件，也没有需要跳过的用户指令，同样保持原 PC。

### Q3：非法指令为什么进入 M-mode，而系统调用进入 S-mode？

PKE 通过 `medeleg` 选择异常的目标特权级。用户 `ecall` 被委托给 S-mode，因此由 `scause` 和 S-mode trap handler 处理。非法特权指令没有被委托，硬件直接进入 M-mode，使用 `mcause`、`mepc` 和 M-mode trap vector。所以不能在非法指令 handler 中调用面向系统调用号的 `do_syscall()`。

### Q4：用户态传入的指针为什么不能直接在内核解引用？

开启 Sv39 后，用户指针是当前进程地址空间里的虚拟地址。内核必须使用 `current->pagetable` 做 page walk，检查 PTE 有效性和权限，再得到物理地址或可访问的内核地址。不同进程可以有相同虚拟地址，因此不能用全局页表或其他进程页表。教学版本只实现了有限的单页转换，完整内核还应检查跨页 buffer、长度、读写权限和地址溢出。

### Q5：`fork` 为什么共享代码但复制数据？

代码段通常是只读可执行的，父子进程共享它可以减少复制开销；数据段包含全局变量和可修改状态，必须复制，否则一个进程修改全局变量会影响另一个进程。COW 进一步把数据复制推迟到真正写入，但前提是父子 PTE 都必须去掉写权限并设置 COW 标志。

### Q6：COW 为什么必须修改父进程 PTE？

fork 后父子共享同一物理页。如果只把子进程设为只读，父进程仍然可以直接写共享页，绕过缺页处理，造成数据竞争和隔离破坏。因此父子双方都要去掉 `PTE_W`，写入时由 fault handler 复制出私有页。

### Q7：COW 为什么需要物理页引用计数？

同一物理页可能同时被父子页表引用。第一个进程解除映射时不能直接 `free_page`，否则另一个进程会访问已经回收的页。引用计数归零时才把物理页放回空闲链表；COW 复制成功后，旧页引用数减一，新页由当前进程独占。

### Q8：`yield` 和时间片轮转有什么区别？

`yield` 是协作式调度，当前进程主动调用系统调用并把自己放回 READY 队尾；时间片轮转是抢占式调度，定时器中断累计 tick，达到阈值后内核自动把当前进程放回队尾。两者最终都使用 ready queue 和 `schedule()`，区别在于触发者是用户主动行为还是硬件 timer。

### Q9：信号量 P/V 为什么有等待队列？

当 P 发现 `count == 0`，进程不能继续运行，也不能留在 READY 队列，否则会忙等或被错误调度。它应该进入该信号量自己的 BLOCKED 队列。V 有等待者时直接唤醒一个进程，而不是先增加 count，因为释放的资源已经交给这个进程。

### Q10：两个 hart 同时分配物理页会发生什么？

空闲页链表的“读 head、更新 head”不是天然原子的。两个 hart 可能读到同一个 head，返回同一个物理页，导致两个进程写同一页。需要用原子交换实现自旋锁保护链表操作。锁只保护短临界区，不能覆盖可能递归分配页表页的整个映射流程。

### Q11：为什么多核启动需要 barrier，单次 HTIF 请求加锁还不够？

HTIF 请求锁只能保证某一时刻只有一个 hart 使用接口，不能保证 `spike_file_init()` 只执行一次，也不能保证其他 hart 不在共享初始化完成前继续运行。因此 hart0 完成一次性初始化后，所有 hart 必须进入 boot barrier，等计数达到 NCPU 才继续。

### Q12：硬链接和复制文件有什么区别？

复制文件会创建新的 inode 和新的数据块；硬链接只在目录中增加一个新的名字到同一个 inode 编号的映射，并把 inode 的 `nlinks` 加一。因此两个路径共享文件内容。unlink 一个名字只减少链接数，只有链接数变成 0 才释放数据块。

### Q13：VFS 为什么需要 `i_ops`？

VFS 只定义通用对象和操作接口，底层文件系统通过 `vinode->i_ops` 提供具体实现。这样 `open/read/write/lookup/link` 的上层流程不需要了解 RFS 的 inode 块布局，也能支持 hostfs 等不同后端。

### Q14：你遇到过什么实际问题？如何定位？

在 `app_hardlink` 还没进入硬链接测试时，Spike 在 ELF loader 的 `size < PGSIZE` 断言停止。我先复现并确认问题发生在程序装载阶段，而不是 `rfs_link()`；然后用 `readelf -lW` 查看 LOAD segment，发现第一个段是 4940 字节，超过 4096 字节页。最后把 loader 改成按段计算页数、逐页分配和映射、按页切片读取，并保持 BSS 清零。修复后程序进入硬链接 TODO，随后实现 RFS link 并重新构建运行验证。

### Q15：这个项目还存在哪些限制？

这是教学内核，不是生产级操作系统。当前限制包括固定的两 hart 支持、简化的用户指针检查、部分实验仍假设单页代码段、进程退出时完整页表回收不充分、文件系统元数据更新缺少完整事务回滚，以及调度器和 RFS 的并发保护比较简化。如果继续改进，我会先建立统一的进程地址空间区域元数据和完整 VM teardown，再补充跨页用户 buffer 校验、更严格的锁粒度和文件系统错误恢复。

## 12. 局限性和下一步改进

### 12.1 当前实现的教学性质

1. **固定多核规模**：多 hart 逻辑按课程要求固定在 `NCPU=2`，不是动态 CPU 管理；
2. **用户指针校验有限**：只完成了必要的单页转换，没有做完整的跨页 buffer、权限和长度检查；
3. **地址空间回收不完整**：进程退出时不能总是立即拆除正在使用的完整 VM；
4. **部分 fork 逻辑按实验假设实现**：早期代码段复制/共享逻辑以课程程序的小段布局为前提；
5. **物理内存分配器简单**：只有页粒度空闲链表，没有伙伴系统或 slab；
6. **RFS 更新不是完整事务**：目录项、inode 链接数和数据块更新分多个步骤；
7. **并发范围有限**：物理页链表有锁，但调度器、VFS 和 RFS 的并发保护不是生产级实现；
8. **未实现后续实验**：相对路径、`exec`、shell、poll、PLIC 和 host device 不在本次范围内。

### 12.2 如果继续实现，优先级

第一优先级是完整进程地址空间生命周期：建立统一 VM region 描述，区分代码、数据、堆、栈、trapframe 和页表页，在进程退出或 `wait()` 回收时安全释放叶子页和页表层级。

第二优先级是健壮的用户内存接口：

~~~text
检查起始地址和长度溢出
逐页确认映射和读写权限
把用户地址安全复制到内核缓冲区
~~~

第三优先级是并发和文件系统一致性：为 ready queue、进程状态转换和 RFS 元数据更新明确锁粒度，用日志、事务顺序或可回滚操作保证中途失败时的一致性。

第四优先级是更完整的进程创建：把多页代码段、数据段、COW heap 和权限复制统一成基于 region 的实现，不再依赖“代码段小于一页”的早期课程假设。
